# Agent 协作一页复盘

## 项目与协作方式

本项目围绕“数据不出企业”的大模型分割推理，依次完成安全方案与攻击评估、基础分割推理、跨地域调度优化，以及给定模型、硬件和 SLO 的容量估算。我的协作原则不是直接接受 Agent 的答案，而是由我定义问题、约束和验收标准，Agent 负责实现与重复实验，再根据异常结果共同修正。

## Agent 帮了什么

Agent 提高效率最明显的地方是把开放问题快速转化为可运行、可检查的工程证据：

- 将 Q1～Q4 拆成威胁模型、Hidden State 反演、HTTP 分割推理、链路与调度仿真、容量预测等可验证子问题；
- 实现 MiniMind 分割推理、噪声消融、500 km/10 Gbps 共享链路、离散事件容量模型和一键运行脚本；
- 自动执行多组实验，生成 JSON、图表和对比矩阵，并持续把结果回写到 README；
- 用 Qwen3-1.7B 补充输出对齐、GSM8K 和安全—可用性实验，避免结论只建立在能力较弱的 MiniMind 上；
- 整理仓库依赖、模型下载与校验流程，使第三方能够从干净环境复现。

## Agent 哪里出错

Agent 的主要问题不是代码生成速度，而是容易在证据不足时过早解释结果。早期短时容量实验没有充分暴露 CPU 热态和尾部抖动，却被当成稳定容量；Q4 最初使用的排队近似偏乐观，不能解释 Q3 的端到端结果；Qwen3 首次 GSM8K 实验错误地合并 System 与 User 消息，造成前 13 题仅答对 1 题；部分脚本最初还隐含依赖仓库外的 tokenizer 和本机模型路径。这些问题说明“脚本能运行”并不等于“结论可信、项目可复现”。

## 我如何纠偏

我持续追问“是否真正执行了模型”“数据和逐题结果在哪里”“原始与分割模型是否答对同一道题”“预测为什么偏离实测”，并要求所有比较统一到相同资源、链路、负载和 SLO。容量实验被延长并重新寻找稳定边界；Q4 改为逐 Token 离散事件模拟，并用 Q2 的阶段耗时和 Q3 的开放到达率实验分层校准；GSM8K 在发现模板异常后立即停止，改用与原始评测一致的 ChatML 模板，最终得到 27/50；交付前又从干净克隆视角补齐下载、校验和路径依赖。

## 最终认识

Agent 很适合快速实现、自动化实验和整理证据，但不能替代对实验设计与结论边界的判断。最有效的协作闭环是：**人定义问题与验收标准 → Agent 实现并实验 → 人检查异常与反例 → Agent 修正代码、模型和文档**。对关键结论，必须同时核查实验条件、原始输出、运行时长、随机性、预测误差以及“实测还是外推”。这比一次性得到一个看似完整的答案更可靠，也是本项目最大的协作收获。
